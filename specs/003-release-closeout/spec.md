## 使用场景与验收

### US1 · 维护者确认当前候选提交可发布（P1）

维护者需要在当前 HEAD 上得到可复核的测试证据，并确认最新提交的多平台 CI 结果。若 CI 无法从当前环境查询，必须明确记录失败原因和最短复核方式，而不是沿用旧提交的结论。

**独立验收**：在干净工作区运行仓库既有测试命令，记录提交、解释器、命令和通过数；CI 结果要么给出当前 HEAD 的链接与结论，要么标为“未验证”并说明解除条件。

**验收场景**：

1. 给定工作区干净且依赖可用，当运行既有测试命令，则记录通过数和运行环境，并与提交哈希对应。
2. 给定 GitHub 凭据不可用，当尝试查询 CI，则记录查询失败原因，并明确说明“不能据此声称 CI 通过”。

### US2 · 交付记录如实反映完成度（P1）

验收记录需要区分“已通过”“脚本化通过”“阻塞未验证”和“已知限制”。Anthropic 真实服务验证、外部用户试用和 I06 兼容性复测属于本轮无法在本机完成或未通过的项目，应保留在记录中并给出解除条件，不能被文档同步成已完成。

**独立验收**：逐项检查验收记录中的未完成项，每项都有当前状态、阻塞原因和解除条件；没有把模拟验证或固定判定包装成真实验证。

**验收场景**：

1. 给定 Anthropic 凭据不可用，当检查 T009，则记录仅完成本地协议演练，真实服务验证待凭据。
2. 给定没有外部试用者，当检查 T010，则记录试用步骤已准备但反馈未收集。
3. 给定 I06 复测失败，当检查发布记录，则能定位固定判定结果与真实兼容性失败的差异。

### US3 · 路线图与验收记录保持一致（P2）

`plan.md` 的阶段二至阶段四需要按实际代码和验收证据更新，已完成项勾选，未验证或明确不支持的范围保持未完成并注明。历史证据可以保留，但当前状态不能与 `specs/` 矛盾。

**独立验收**：对照 `docs/terminal.md`、`specs/001` 和 `specs/002` 的证据，逐项核对 `plan.md` 的勾选状态；每个新勾选项都能指向代码或验收记录。

**验收场景**：

1. 给定某能力只有文档声明而无验收证据，当更新路线图，则保持未勾选并注明待验证。
2. 给定某能力已由测试或真实任务验证，当更新路线图，则勾选并注明证据位置。

### 边界情况

- GitHub 查询失败或凭据无效时，不得把旧提交的 CI 结果写成当前 HEAD 的结论。
- 测试解释器不一致（例如主环境缺少测试依赖）时，记录实际使用的解释器，不写成“所有环境通过”。
- 模型调用会产生费用；本轮除已有本机测试外不新增付费请求，除非用户明确授权。
- 文档同步不得修改历史验收事实，只更新当前状态和指向。
- 本特性不包含产品代码行为变更；发现需要改代码的问题时单独立项。

## 需求

### 功能需求

- **FR-001**：记录当前 HEAD 的测试结果，包含提交、解释器、命令、通过数和运行日期。
- **FR-002**：记录当前 HEAD 的 CI 状态；无法查询时说明原因和最短复核方式，并保持“未验证”。
- **FR-003**：把 T009、T010 记录为阻塞项，分别给出阻塞原因和解除条件。
- **FR-004**：把 I06 兼容性复测结果记录为已知限制，包含失败表现、影响范围和现有检查位置。
- **FR-005**：按证据更新 `plan.md` 阶段二至阶段四的勾选状态；无证据项保持未完成。
- **FR-006**：确保 `plan.md`、`docs/terminal.md` 和 `specs/` 对当前版本的完成度描述不互相矛盾。
- **FR-007**：交付记录中不出现密钥、令牌或真实用户数据。

### 关键实体

- **候选提交**：版本号、提交哈希、测试环境、测试通过数、CI 结论。
- **验收项**：编号、状态（通过 / 未验证 / 阻塞 / 已知限制）、证据位置、阻塞原因、解除条件。
- **路线图条目**：阶段、能力描述、勾选状态、证据位置。

## 成功标准

### 可衡量结果

- **SC-001**：当前 HEAD 的测试命令有至少一次实际运行记录，通过数可复核。
- **SC-002**：所有未完成验收项 100% 具备状态、阻塞原因和解除条件。
- **SC-003**：`plan.md` 中每个新勾选项都能对应到代码、测试或验收记录，零无证据勾选。
- **SC-004**：交付文档中不包含密钥、令牌或真实用户数据。
